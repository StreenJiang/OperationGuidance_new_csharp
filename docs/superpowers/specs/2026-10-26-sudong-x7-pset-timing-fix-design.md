## 1. 问题

速动 X7 在换点位时偶发「程序号下发失败」，UI 显示「正在重连重试」，工具被锁，最长可持续 20 秒以上才恢复；期间设备实际仍停留在旧程序号。

7 天日志（1,235 次程序号切换）统计：

| 指标 | 数值 |
|---|---|
| PSet 1（任务激活时下发） | 1,235 次发送 / 1,235 次成功（100%） |
| PSet 2（拧紧完成后切换下一个点位） | 4,023 次发送 / 1,235 次切换成功 / 2,788 次超时 |
| 首次下发即成功 | 111 次（9.0%） |
| 单次切换耗时 | 中位 1.3s，平均 2.5s，最长 20.5s；>5s 115 次，>15s 12 次 |
| 重试发送成功率 | 约 40%（1,124 / 2,788） |
| 设备显式拒绝（ERROR_RSP） | 0 次 |
| 发送失败 / 解析异常 | 0 次 |

## 2. 证据

### 2.1 首次失败与「距拧紧结果帧的时间」100% 相关

以 `55AA2781` 拧紧结果帧为基准，统计 PSet2 **首次**下发：

| 距结果帧 | 结果 |
|---|---|
| < 0.75s | 1,179 次 → **1,179 次超时（100%）** |
| 0.75–0.93s | 临界区（超时/成功混合） |
| ≥ 0.93s | 48 次 → **48 次成功（100%）** |

「偶尔成功」的直接原因是 DB 写入耗时偶尔变慢：PSet 在 `StoreDataToDatabaseAsync` 完成后立即发出（`waitAfterDB ≈ 0.01s`）。DB 写得快 → PSet 落在设备忙碌窗口内 → 失败；DB 写得慢（≥0.9s）→ 恰好越过窗口 → 成功。

### 2.2 超时期间设备完全静默

- 每天 `Data received, length` 与 `dataMessage` 行数 1:1 相等（894/894 … 3010/3010）
- 失败窗口内未收到任何字节
- 说明不是 ACK 被粘包吞掉（那种情况会留下 `dataMessage`），而是设备未响应

### 2.3 设备确实停留在旧程序号

X7 结果帧携带当前激活程序的扭矩上下限（现场两套程序分别为 900–1100 与 400–600）。失败风暴期间操作工踩扳机产生的结果帧，上下限仍是旧程序。

### 2.4 重连执行正确，但不解决问题

对 2,788 次重试做严格代码顺序审计：

| 审计项 | 结果 |
|---|---|
| 旧 RunTask 先退出再重连 | 2,788/2,788 |
| 新建 socket | 2,788/2,788 |
| 新接收循环启动后才发 PSet | 2,788/2,788 |
| 双重连接 / 残留任务 / 跳过连接 | 0 次 |
| `reconnected after` | 2,787 次 = 200ms |

**重连在 socket 层完全正确。失败发生在 socket 之上。**

### 2.5 重试的 PSet 总是撞进锁/解锁序列

- `ForceUnlock → Sending PSet`：中位 **206ms**（2,776/2,788 落在 200ms 桶）
- `PerformUnlock`/`PerformLock` 内部是「发送 → `Thread.Sleep(200)` → 再发送」
- 因此 PSet 固定落在第二条解锁/加锁命令前后 1ms 内
- 1,584 次伴随加锁的重试中，1,479 次 PSet 在 `Locking` 后 200ms 内发出

### 2.6 客户端粘包会丢 ACK（重连无法修复）

```
2026-10-16 14:21:21,763  dataMessage = 55AA0585007B450D0A55AA058205B9760D0A
2026-10-21 14:23:46,165  dataMessage = 55AA0585007B450D0A55AA058205B9760D0A
```

`ToolSudongX7.AnalyzeData` 对整包做字符串精确比较，两帧粘连时 PSet ACK 被丢弃。两次都可从后续结果帧确认设备**已切换到程序 2**。

### 2.7 其他风险

- 失败窗口内 App 认为已锁枪，但设备无锁枪反馈；日志中 16 次在重试等待期间收到操作工的拧紧结果帧
- PSet ACK 为固定帧 `55AA058205B9760D0A`，不携带程序号，无法证明设备真正切换
- ACK 在 `_sendingPSet == -1` 时被静默忽略且无日志

## 3. 根因

1. **下发时机错误（主因）**：X7 在拧紧结果产生后约 1 秒内不处理上位机指令；App 在结果存储完成后立即下发 PSet。
2. **重试复刻失败条件**：`Connect()` 在 `ForceSendUnlock()` 之前置 `Status = CONNECTED`；200ms 轮询使每次重试的 PSet 恰好落在强制解锁/加锁序列中。
3. **帧解析不具备 TCP 流式语义**：粘包导致 ACK 丢失，重连无法修复。
4. **缺少设备就绪判据**：X7 无握手，`Status == CONNECTED` 只代表 TCP 连通，不代表设备可接收指令。

## 4. 设计决策

### D1：协议不可改
所有改动仅在上位机侧完成。

### D2：X7 专属行为隔离
新增的静默窗口、命令闸门、帧解析按 `_toolType is ToolSudongX7` 分支启用；PF/FIT 的握手、心跳、PSet 流程保持不变。其中命令闸门只在 `_toolType is ToolSudongX7` **且** `PSetQuietWindowMs > 0` 时启用（`0` 时闸门与静默窗口一并关闭）。

### D3：帧解析改为「长度前缀 + 重组」
速动帧满足 `总长 = len + 4`（len 为第 3 字节），帧尾固定 `0D 0A`。新增 `SudongFrameCodec`：
- 一次 `Receive` 可拆出多帧
- 半包留在缓冲区等待下次
- 非法长度/帧尾时逐字节重新同步
- 缓冲区上限 8KB，超限清空并告警

### D4：PSet 前增加「设备静默窗口」
`PSetQuietWindowMs`（默认 **1200ms**，ini 键 `pset_quiet_window_ms`，范围 [0, 10000]，**0 = 关闭**）：
- 距最近一次拧紧结果帧 ≥ 窗口
- 距最近一次指令发送（锁/解锁/PSet）≥ 窗口
- 两个条件同时满足才发送

该窗口对 PSet 1（任务激活）同样生效；正常情况下任务激活距上次指令通常 >1.2s，不会额外等待；若恰好刚发生过锁/解锁，最多延迟 1.2s。

依据：首次下发 <0.75s 全败、≥0.93s 全成。取 1200ms 是为覆盖**客户端接收延迟**：接收循环是 `Receive(200ms 超时) → 处理 → Task.Delay(100ms)`（`LoopingInterval = 100`），结果帧到达 socket 后最坏约 100ms 才被处理，`_lastRundownAtMs` 因此比设备实际发送时刻晚最多约 100ms。1000ms 证据边界 + 100ms 接收延迟 + 100ms 调度余量 = 1200ms。若后续调小 `LoopingInterval`，该窗口可同步调小。

### D5：命令闸门（只保护最后一次发送）
新增 `SemaphoreSlim _commandGate`：
- 静默等待在闸门之外，避免阻塞 UI 线程（`ForceSendLock` 在 UI 线程调用）
- 闸门只保护「最后一次静默复核 + `SendCommand`」，PSet 侧持有时长约一次 `Send`；锁/解锁侧持有时长是原有「双发 + `Thread.Sleep(200)`」的约 200ms，不是静默窗口的 1.2s
- **不跳过** `SendLock` / `SendUnlock`：LockCheck 只在状态切换时真正发送，不会持续刷新静默窗口；让加锁先发生、PSet 以最后一次锁命令为基准重新计时，等待期间工具保持锁定（安全），避免「跳过加锁导致约 2 秒无锁」的空档
- 杜绝 PSet 插入锁/解锁序列，也杜绝锁/解锁插入 PSet 发送瞬间

### D6：不修改 `Connect()` 的置位顺序（评估后取消）
原先计划把 `ForceSendUnlock()` 移到 `Status = CONNECTED` 之前。复核后取消：`SendPSetAsync` 的静默窗口会在强制解锁第二发之后重新计时，命令闸门再保证发送瞬间不交叠，因此「PSet 抢先于强制解锁」的竞态已被完全覆盖。保持 `Connect()` 原样可让 PF/FIT 真正零影响；`pset_quiet_window_ms = 0` 时静默窗口与命令闸门同时关闭（帧解析修复保留），行为与改动前完全一致，便于 A/B 对比。

### D7：可观测性
新增连接世代号、本地端口、原始收发帧、PSet 上下文、迟到 ACK 告警、结果帧结构化摘要、短写检测。用于下一版现场日志验证设备侧规则。

### D8：生产安全（客户无法现场测试，一次性上线）
- **fail-open**：静默等待超时、闸门超时、解析异常都返回失败并交给现有重连重试，不新增失败模式
- **有界等待**：静默等待上限 `max(3 × PSetQuietWindowMs, 3000ms)`；命令闸门 `Wait/WaitAsync(2000ms)`，超时记日志并回退
- **解析层回归**：用 7 天日志中的真实帧（9/18/43 字节，含 `IS_TIGHTENING + PSET_OK` 粘连对）做逐字节回放测试，并加随机字节 fuzz 保证不抛异常
- **一键回退**：`pset_quiet_window_ms=0` 同时关闭静默窗口与命令闸门（帧解析修复独立保留），恢复到改动前的时序行为
- **部署后观察附录**：计划末尾给出 grep 清单与回退判定条件

### D9：长尾（15–22s）不做自适应加重
- 现象：少数失败跨多次重连、持续 15–22s；期间设备完全静默。
- 决策：本版不做窗口翻倍/自适应加重；靠现有重连重试 + 新增诊断日志分类原因。理由：长尾在累计等待 15–22s 后仍失败，说明不是「再等 1 秒就好」，盲目加倍大概率无效且会拖慢恢复。
- 后续：根据现场日志区分「窗口已满足但设备不回 ACK」「`epoch` 递增但无帧」「迟到 ACK」「客户端解析异常」，再决定是否加自适应或改变策略。

### D10：不做的事
- 不修改协议、不改固件、不要求设备回显程序号
- 不重构 PF/FIT 分支
- 不引入新的第三方库
- 不改数据库结构

## 5. 风险

| 风险 | 缓解 |
|---|---|
| 静默窗口增加切换延迟（最多 1s） | 现状中位 1.3s、长尾 20s；窗口后预期中位约 1.2s、长尾减少 |
| 静默等待期间加锁会刷新窗口 | 这是预期行为：先加锁、再等 1.2s、再下发，保证等待期间工具处于锁定状态；LockCheck 只在状态切换时真正发送，不会饥饿 |
| ~~延迟置 CONNECTED 影响 PF 重连时序~~ | **不再适用**：该改动已取消，`Connect()` 保持原样 |
| 帧解析改动影响 PF/FIT | 仅接入 X7 分支，PF/FIT 继续走原 `AnalyzeData` |

## 6. 验收标准

1. 单元测试：粘包/半包/垃圾数据均正确解析，粘连的 `IS_TIGHTENING + PSET_OK` 能触发 PSet 成功。
2. 集成测试（Mock X7）：
   - 设备在结果帧后 600ms 内忽略 PSet，App 设置 800ms 静默窗口后首次下发成功
   - 关闭静默窗口时复现超时（守住根因）
   - 强制解锁与 PSet 串行，PSet 是序列中最后一条命令
3. 回归：现有 PF/FIT 单元与集成测试全部通过。
4. 现场：部署后日志中 `PSet sending timeout` 相对 4,023 次发送的占比显著下降；`PSet ACK with no PSet in flight`、`frame=UNKNOWN`、`Partial send` 可统计。
